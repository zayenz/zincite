Zincite helps you review and maintain MiniZinc models. The formatter takes care
of layout, so an edit to a constraint produces a diff you can read. The linter
checks conventions and looks for modelling concerns, such as mismatched array
indices or expressions that may be undefined. Queries let you inspect the
source and data when you have a more specific question.

The commands work without running a MiniZinc compiler or solver. They share a
parser that keeps comments, spelling and source locations, so findings can
point back to the model you are editing.

## A staffing example

Suppose we are staffing three days. Each day has a required number of people
and a number available. A fragment of the [staffing model](./guides/first-model/)
starts like this:

### Formatting constraints

<div className="format-comparison">
<div>

#### Before formatting

```minizinc
% Staff cannot be moved from one day to another.
constraint forall(d in Days)(staff[d]>=required[d]);
constraint forall(d in Days)(staff[d]<=available[d]);
```

</div>
<div>

#### After formatting

```minizinc
% Staff cannot be moved from one day to another.
constraint forall (d in Days) (
    staff[d] >= required[d]
);
constraint forall (d in Days) (
    staff[d] <= available[d]
);
```

</div>
</div>

`zincite fmt staffing.mzn` prints the formatted model. The quantifiers and
bodies have room to be read separately; the names and comment stay intact.
Add `--write` to apply the layout, or `--check` to check it in CI.

### Linting constraint labels

Run the naming and constraint-label checks:

```sh
zincite lint --isolated --rules naming,missing-constraint-label staffing.mzn
```

This reports a `missing-constraint-label` warning at each constraint. A label
such as `constraint :: "Cover each day's demand"` tells a reader what the
first constraint means. Zincite leaves that wording to the modeller. The
[walkthrough](./guides/first-model/#linting-constraint-labels) shows
the labelled version and explains the selected checks.

### Querying staff shortages

Now consider the data:

```minizinc
required = [2, 3, 4];
available = [3, 4, 3];
```

There are ten staff-days available for nine staff-days of demand. But a spare
person on day 1 cannot fill a gap on day 3. A short query makes that visible:

```zirql
let required = items | filter(name("required")) | values | one;
let available = items | filter(name("available")) | values | one;
[
    (day: d, missing: required[d] - available[d])
    | d in index_set(required)
    where required[d] > available[d]
];
```

Save the data as `staffing.dzn` and the query as `shortages.zq`, then run:

```sh
zincite query --program-file shortages.zq staffing.dzn
```

The JSON report contains one row: day **3** is missing **1** person. This
checks the literal arrays, which have the same indices in this example. It
does not solve the model. The query gives us a concrete data problem to
investigate before asking a solver for a roster.

[Work through the complete example](./guides/first-model/) for the model,
formatter output, lint feedback and query result.

## Install from source

Use a current stable Rust toolchain. The packages on crates.io are name
reservations; install the working commands from a checkout.

Zincite is in early development. Formatting and interfaces may change,
including changes that break existing workflows. The
[support guide](./guides/support/) explains language coverage and how to
interpret incomplete analysis.
